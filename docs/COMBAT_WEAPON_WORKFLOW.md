# 三维动作武器：工作流与注意事项

本页总结长剑、打刀、长枪、和弓几轮的做法和踩过的坑，以后加同类武器时照着做。字段和格式的规定看 [战斗骨架与兼容性规范](COMBAT_SKELETON.md)，单把武器的设计看它自己的文档；这里只写“怎么做、要注意什么”。

| 武器 | 设计文档 | 导入脚本 | 编排脚本 | 客户端场景 |
|---|---|---|---|---|
| 曦誓、黑钢长剑 | [LONGSWORDS.md](LONGSWORDS.md)、[DAWNVOW_CHARGE.md](DAWNVOW_CHARGE.md) | `import_longswords.py` | `longsword_moves.py`（被弹反）、`dawnvow_moves.py`、`blacksteel_cast_moves.py`（其余动作是美术手做） | `group:longsword` |

## 1. 几条原则

- **兼容性优先。** 规范第 1 节高于任何新功能：只接管本附属的物品，伤害走原版流程，平时完全原版，出错退回原版。
- **写武器怎么走，不写骨骼角度。** 编排给出握点、刀尖和刃的方向、躯干、脚步，手臂和腿由 `tools/combat_author.py` 解出。同一份编排烘焙到第三人称、第一人称和 NPC，不用运行时重定向。
- **服务端决定时机，客户端只画。** 出招、接触、效果都在招式状态机里；客户端按同步来的招式取样。
- **好不好看由维护者试玩决定。** 打刀的手腕、破面、手肘、格挡缩进身体，和弓的转身方向、弓的大小，都是自动检查全部通过之后才在试玩里发现的。检查只能证明没坏。

## 2. 流程

1. **查美术交付**（第 3 节）。结论写进武器文档第 1 节；需要维护者定的（例如刀太长）先问，其他按规范处理。
2. **定玩法和招式表。** 先列招式、时长、接法和输入，画出状态图，再做动作。能借 TLM 的只有移动类动作（走、跳、受击，署名见 [CREDITS.md](../CREDITS.md)）；TLM 没有双手武器动作，武器动作都要自制。
3. **写导入脚本。** 网格、贴图、图标、物品模型都由脚本从仓库外的美术目录生成，不手改生成的 JSON。
4. **写编排、烘焙、看离线预览。** `combat_render.py` 画总览图和 GIF，刀尖轨迹是红线。先在预览里看幅度、穿插、入地，再进游戏。预览放仓库外的 `art/<武器>/anim_vNN`，每轮换新目录，不覆盖旧版。
5. **接 Java。** 物品实现 `CombatWeapon.Holder`，注册固定编号（代码里全局搜 `CombatWeapon.register`，取没用过的号）；写招式文件、语言、创造模式物品栏（`AddonTabs.WEAPONS`，同类武器挨着放）和标签。
6. **写测试**（第 8 节）：单元测试、客户端场景、人工看截图。
7. **给维护者试玩**，按反馈改编排、重新烘焙，再过一遍第 6 步。
8. **写文档和验证记录**，维护者说可以再提交、开 PR（第 9 节）。

## 3. 美术交付检查

| 查什么 | 为什么 | 遇到过的情况 |
|---|---|---|
| 网格原点、刀尖方向、握点位置 | 编排和手的目标都按它算 | 打刀原点在柄与镡之间、主副手 0.65 / −1.1；长枪原点在主握点，手要沿杆滑动 |
| 配色是否共用几何和 UV | 共用才能共用动作，只换贴图 | 打刀、和弓四套配色都共用 |
| 贴图尺寸是否正方形 | UV 要按横纵分别归一化 | 长枪 32×40 |
| 物品模型是否等于网格 + (8, 1, 8) | 魔力缠绕按物品模型表面定位（第 7 节） | 长枪交付缩到 0.65 倍，要重新生成，并换算展示变换 |
| 武器长度与使用者手臂的比例 | 太长时拔刀、收刀手够不到 | 神狐用 2 倍刀时刀长是手臂的 2.8 倍，改成 1.6 倍，再加大拉鞘 |
| 武器相对使用者身高 | 武器缩放放在网格的 `scale` 上，不改物品模型 | 和弓第三人称 1.3 倍身高；物品模型不放大，骷髅手里的大小不变 |
| 活动部件是否分了骨骼 | 弯曲、拉伸要靠骨骼 | 和弓弓身 17 节、两段弦和搭箭点，都挂在 `Weapon` 下 |
| 缺什么 | 箭矢、图标这类要自己补 | 和弓交付没有箭；打刀、和弓的图标由配色生成（打刀的是占位） |

## 4. 编排与手臂

玩家方块手臂没有手腕，大多数姿势问题都从这里来。下面这些在 `rigid_arm` 里已经处理，**不要改回去**；新武器沿用就能避开。

| 症状 | 原因 | 做法 |
|---|---|---|
| 手腕折过去，很难看 | 按真人手腕算手部朝向 | 手与前臂一体，只用肩和肘；对不齐的部分表现为刀柄斜穿拳心，这比折手腕好看 |
| 肘部破面、棱角穿插 | 前臂连续自转，方块袖子在肘部错开 | 前臂只转 0°、±90°、180°（`TWIST = None`），换档有代价 |
| 第三人称手肘外翻 | 只顾拳心对刀柄，手肘权重太低 | 手臂自然优先于刀柄对齐：`ELBOW_PREF`、抬肘扣分 |
| 手臂缩进身体 | 求解不看身体，双手离胸口太近 | 骨架给 `body` 盒子，穿进去重罚；同时把武器往前推 |
| 拿着武器时手臂别扭 | 待机姿势本身没有手腕就握不正（刀尖斜指前下） | 改编排，不靠求解器救：待机刀尖接近水平朝前 |
| 手臂上有黑色条带 | 细臂皮肤按宽臂取 UV，空白列被原版变成黑色 | 宽、细两套手臂网格（#146）。开发账号 Dev 用的就是细臂 Efe |
| 手像拼起来的拳头 | 手掌、四指、拇指分开建 | 手是一整块，截面同前臂，和原版一样 |
| “手臂伸直”做不直 | 调握点试出来的总差一点 | 按臂长算握点（和弓的 `straight` / `reach_out`），再用单元测试量肘弯 |

写关键帧时注意：

- 动过 `grip` 的关键帧必须同时写 `blade`、`edge`，否则朝向不对。
- 需要在某帧停稳就加 `ease='hold'`，否则切线会把相邻的动作带歪。
- 比例差太多时用只对某副骨架生效的字段（`fox=dict(...)`，也可以是 `player`、`fp`），不要为 NPC 另写一份编排。
- 烘焙会打印够不着超过 5% 臂长的时段和刀柄偏角，每次都要看。短暂差约 0.08 臂长看不出来；手和武器明显脱开就要改。
- 相邻两个关键帧的 `blade` 或 `edge` 差过 90°、尤其接近反向时，中间补一帧，把弧线该经过的方向写出来。`blade`、`edge` 是按分量插值再归一化的，两头相消时刀会在一帧里翻过去，刀光也会变成一块平板（神狐打刀 slash_1 曾一帧转 145°）。`Baker` 会报“刀翻面”（插值向量短于 0.3，或刀一帧转过 75°），`Baker(sk, strict=True)` 时直接报错。
- 长武器转圈要看地面。枪竖着转会扫到地，所以拔枪改成头顶平转，竖直面的转枪放到身体侧面；打刀第一版蓄势时刀尖也入过地。预览和单元测试里都查最低点。
- 手沿杆滑（`rpos` / `lpos`）、前手不动杆滑过（`lmode: slide`）、杆在拳中转（`raxial`）、按武器坐标摆手（`rweapon` / `lweapon`）、整身转身（`turn`）都已经有了，先用现成的。

玩家只替换双臂和躯干转向，腿只叠加张开的 Z 旋转。弓步、髋部下沉只有 NPC 看得到，所以动作只靠手臂和躯干也要成立。

## 5. 第一人称

第一人称要单独取景，不是第三人称的副本：

- 用 `player_fp.json` 单独烘焙，同名标记必须和第三人称同一时刻。
- 架势低的武器手和武器都在画面外：打刀整体前移抬高（`reach`），待机另写第一人称版本（`IDLE` 的 `fp` 覆盖）。
- 转身的武器要移开身体：和弓把身体压低左移，手的目标按镜头坐标写（`fpv`），贴着镜头的前臂缩成 0（`rhide`）。
- 刺击类要校准落点：长枪给了整体偏转（yaw 14°、pitch 6°），枪尖才落在准星附近。
- 截图时看准星是否被挡。

## 6. 招式和服务端

- 改动作时长、`contact`、`cancel` 后要同步改招式文件。导入脚本还不会自动同步（规范第 8 节第 1 条），靠 `clipsMatchTheMovesetInBothViews` 这类单元测试抓不一致，新武器也要写这项测试。
- `at` 不能早于最后一个 `contact`，否则缓冲的下一招吞掉命中。
- 右键转格挡要立刻切：不排队（不写 `queue`），`blend_in` 短。原版盾的前摇来自 `blocks_attacks` 的延迟，设 0 即可。
- 按住右键时原版会吞掉左键：招式接受这时的左键时，客户端自己取走按键发给服务端（打刀突刺、黑钢蓄力都靠这个）。
- 变体优先继承：招式文件用 `extends`，动作文件用 `<网格>_<视角>.animation.json` 盖在共用动作上（曦誓、黑钢长剑）。
- 想让生物当原版武器用，就继承原版类。`YumiItem` 继承 `BowItem` 并加进骷髅和附魔标签，生物走原版 AI、射原版箭；视野拉近只对原版弓生效，要自己补。
- 改变目标状态要能恢复：浮空临时开 NoAI 时打标签，卸载再加载后按标签恢复。玩家悬空 80 刻会被服务端踢，浮空要封顶（长枪 70 刻）。
- 高频多段伤害要关掉击退和攻击冷却衰减（`knockback: false`、`full_strength: true`），否则目标被推开、伤害被冷却吃掉。
- 伤害数值、时长是先定的，等维护者试玩再调；调的时候只动被点名的值。

## 7. 物品模型和特效对齐

- 手持、掉落、魔力缠绕用立体模型，像素坐标 = 网格 + (8, 1, 8)；物品栏和展示框用平面图标（物品定义里按 `gui`、`fixed` 切换）。打刀第一版只有平面图标，缠绕特效就对不上。
- 单元测试检查“物品模型等于网格平移”（`itemModelIsTheMeshOffsetLikeTheOtherWeapons`、`allFourFinishesShareTheMeshAndScale`）。
- 武器要施法时，尖端挂点按 Logos 规范写在物品模型的 `wand_tip` 组，并在两个视角都确认实际坐标（黑钢长剑的场景 `BlacksteelCastView` 把它记进日志 `[cast point]`）。
- 骨骼动作不会带动物品模型：和弓拉满时弓梢和缠绕会有点错位，属于已知限制，要写进武器文档。
- 需要跟随动作的客户端效果，从同步的招式和动作标记自己算（长枪的 `tip_fx`），不另发网络包。

## 8. 工具和测试

**改工具**

- 先看 `combat_author.py` 有没有，有就复用。黑钢那轮另写过一个 `combat_fk.py`，发现重复后删掉了。
- 新功能要通用，并证明不影响旧武器：改完重新烘焙打刀，`git status` 里动作文件应该没有变化（逐字节相同）。
- 运行方式：`uv run --with numpy --with pillow python tools/<脚本>.py …`；本机系统 Python 没有 numpy。

**测试分层**（验证记录里分开写，没测的写明）

| 层 | 查什么 | 命令 |
|---|---|---|
| 单元 | 动作与招式一致、连招时间轴、物品模型、骨骼绑定、数值性质（弦长、肘弯） | `./gradlew --offline test build -PlogosJar=…` |
| 世界 | 伤害、耐久、魔力、服务端效果 | `./gradlew --offline runGameTestServer -PlogosJar=… "-PdimensionTests=logos_dimension:longsword_*"`（只接受一个通配式） |
| 实际客户端 | 真实按键走完整套操作，截图人工看 | `./gradlew --offline runClient -PlogosJar=… -PldTest=group:<武器> -PldTestHeadless -PldTestWindow=1280x720` |

只跑相关的组，不跑整个 `group:logos`（约一小时）。改了共用的渲染层或状态机时，加跑 `group:longsword` 和其他用到它的武器。

**检查要能失败**

- 涉及方向的检查用数值，不要只看截图（下面的事故）。加了检查后，把修复临时改回去跑一次，确认新检查会失败。
- 改的是渲染，失败的却是服务端逻辑：先在不含改动的干净 main 上复现（用单独的工作树，不要 stash），再定性为已有问题，并写进 PR 说明。不要顺手修。
- 客户端偶尔无报告退出时可以重跑，但要把这次退出如实写出来。

**和弓转身方向事故（#153 → #155）。** 第一次做时符号是对的，“在游戏里核对方向”时把侧面截图看反，改成了错的，所有检查照样通过；维护者一试就发现整个人朝反方向。动作里的角度要经过 Blockbench 空间、渲染层翻转、原版 `180 - bodyRot` 三层，靠直觉推符号容易错。现在的做法：

- 取实际画出的骨骼在世界里的朝向，和视线算夹角（`YumiClient.arrowDirection`，余弦 > 0.97）。
- 多取几种状态：拉满、转动视线后、转回来、左手惯用。
- 看图时用盔甲架当镜头从正上方俯视（`YumiView`），不用侧面图判断方向。
- 再做一次反向对照。

**场景和测试的坑**

| 现象 | 处理 |
|---|---|
| 再跑一次 `-PldTest`，上次的截图没了（`build/ldlib2-uitest` 每次清空） | 要留的截图先复制到仓库外的 `art/<武器>/ingame_vNN` |
| 后面的步骤因靶子死了而失败 | 靶子血量给够，或关掉 AI；同一组里算好总伤害 |
| 摔落伤害测不到 | 铁傀儡免疫摔落，用尸壳；用 `LivingDamageEvent.Post` 记录伤害类型和数值 |
| 骷髅着火挡住武器、夜里刷怪打乱伤害 | 切到夜晚并关掉 `spawn_mobs`、`spawn_monsters` |
| 隐藏 HUD 后第一人称的手也没了 | 拍第一人称不要隐藏 HUD |
| 魔力的测量值不对 | Logos 魔力自然回复，被挡术式的游离魔力还会被吸走；测试时关回复、每刻清游离魔力，或断言实际扣费 |
| AI 字段访问不到（`goalSelector`） | 按行为测：骷髅是否真的射出原版箭 |
| 需要等服务端条件 | 用场景的 `waitUntilServer`，不要靠抛异常重试 |
| 看不到双腿 | 原版镜头总在视线上，侧身后只看得到侧面；换俯视或侧面机位，否则写进“未验证” |

**NPC。** 同一份编排烘焙到 NPC 骨架（导出时扣除静止外张角），动作文件并入 NPC 自己的动画，服务端用同一台 `MoveRunner`（打刀见 UCHIGATANA.md 第 6 节）。离线烘焙不等于已接入：和弓的神狐版本目前只烘焙了，NPC 手里还是原版弓，文档和验证记录要分清。

## 9. 分支、PR 和环境

- 每把武器一个工作树（`../worktrees/<名>`），从最新 main 拉分支。主检出常停在别的分支上，不要在那里动。
- **推送前先确认旧 PR 是否已合并。** 打刀 #116、和弓 #153 都是改完才发现已合并，往旧分支推进不了 main，要从最新 main 另开分支（#118、#155）。推送被拒时先看远端多了什么，不要覆盖。
- 开 PR 前合并最新 main，重跑相关测试。`VERIFICATION.md` 顶部常有冲突，两边都保留。
- **Logos jar 经常要换。** main 常依赖还没发版的 Logos，版本号仍是 0.6.0，无法声明下限。编译报缺符号时，先判断错误是不是自己的，再换最新的本机构建；验证记录写明用的是哪个分支、哪个提交。依赖 Logos 新接口时，先合 Logos 的 PR，并在 PR 里写明顺序。
- Windows 上 Python 文本模式写文件会变成 CRLF：写文件用 `newline='\n'`，提交前看一眼 diff 大小或 `git ls-files --eol`。
- 给脚本打补丁时写成文件再运行，长 heredoc 容易出解析错误。
- 试玩包放仓库外 `builds/<武器>-<日期>`，附上配套的 Logos jar、校验值和试玩说明（操作、想听哪些反馈、已知问题）。如果之后又合并了 main，告诉维护者试玩包和 PR 的差别。
- 提交标题用英文，说明用中文，不加 AI 署名。

## 10. 和维护者配合

- 维护者说可以之前只留在工作树，不提交。先给预览和截图，再给试玩。
- 反馈按招式和视角定位（“第三人称格挡缩进身体”），改编排后重新烘焙，并把新截图和旧的对照。
- 只改被点名的部分。“拉弦的手保持现在这样”就要证明没动：那一轮把 `RightArm`、`RightForeArm` 的旋转和放大前的动作文件逐值对比过。
