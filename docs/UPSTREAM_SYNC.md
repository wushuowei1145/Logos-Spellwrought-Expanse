# 与主模组（Logos）同步的检查清单

本附属编译期依赖主模组的 jar（`-PlogosJar`，用于调用 `dev.logos.runtime.Vfx` 等公开类，见 [VFX.md](VFX.md)），所以主模组改了这些类的签名时，编译会报错。
但大部分接入点（标签、注册 ID、反射桥）不经过编译，运行期仍可能撞车：标签语义变化、同名内容、方块/物品行为改动。每次开 PR 前必须过一遍下面几项。

## 一、开 PR 前的固定动作

```text
python tools/check_logos_upstream.py
```

默认在 `../minecraft-logos` 找主模组仓库，会先 `git fetch`。它会检查四件事：

| 检查 | 不通过时的含义 |
|---|---|
| 落后 `origin/main` 多少提交 | 有新提交要先读，可能改了我们依赖的标签/API |
| 依赖范围（`neoforge.mods.toml` 里 `modId="logos"` 的 `versionRange`）是否覆盖当前 Logos 版本 | 覆盖不到就该改范围或改代码 |
| 我们的方块/物品 ID 是否在主模组源码里以完整字符串出现 | 出现就要判断是重复实现还是可复用 |
| 我们追加的标签是否都写了 `replace: false` | 没写会覆盖主模组条目 |

## 二、还要人工确认的三件事

1. **读相关提交**：主模组改标签、改方块注册、改事件顺序时，附属的行为可能变。
2. **用新版本 jar 跑一次**：`./gradlew test runGameTestServer -PlogosJar=<logos-x.y.z.jar>`。
   因为只有运行期依赖，**编译通过不代表兼容**，必须跑世界内测试。
3. **记录在 PR 正文**：写清楚"对 Logos `<版本>`（`<提交>`）验证过"，没验证就写没验证，不许含糊。

## 三、判断标准

| 情况 | 处理 |
|---|---|
| 主模组有新标签 | 跟进追加，不新建平行标签 |
| 主模组有同名材料 | 复用它的注册 ID，不复制方块/物品 |
| 主模组新版本超出依赖范围 | 先跑一次验证，再决定是否抬最低版本；抬了要写进 PR |
| 主模组新增同名但不同功能的内容 | 在 PR 里说明区别，避免下次被当成重复 |
| 主模组改了 `logos:fragile_plants` 之类的语义 | 重新核对我们的植物是否仍然按预期衰退/退化 |

## 四、当前对齐状态（2026-10-25）

| 项 | 状态 |
|---|---|
| 主模组版本 | **0.6.0**（`3755786`，Bump version to 0.6.0） |
| 依赖范围 | `[0.5.0,)`，覆盖 0.6.0 |
| 运行期验证 | 幼年牧草 / 草皮骨粉两处改动已在 0.6.0 的 jar 上跑过定向 GameTest |
| 同名 ID | 无（176 个注册 ID 在主模组源码里没有完整同名命中） |
| 功能相近但不同 | 主模组有 `mercury_mushroom`（炼金罐作物，产出水银），与附属的林地蘑菇（`journey_*_mushroom` 等）不是同一功能 |
| 标签语义 | `logos:fragile_plants` 自主模组 #304 起按标签生效，附属一律 `replace:false` 追加 |
| 不内嵌 | 安装包里不含主模组 jar，玩家自己装 |

## 五、常见坑

- **只看编译**：编译只能检查直接调用的公开类；标签、注册 ID 和反射桥都不经过编译，编译过不能证明跟新 Logos 兼容。
- **改标签用 `replace: true`**：会顶掉主模组的条目，其它植物/树叶就失效了。
- **复制主模组材料**：会多出一份注册和贴图，违反"复用现有材料注册 ID"。
- **把功能分支的合并当成 main 已更新**：主模组那边的更新要另行整合进 main。
